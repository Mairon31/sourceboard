# SourceBoard Design System

This document is the stable visual contract introduced in **Phase 0A — Design System, Liquid Glass and Motion Framework**. Later product phases should consume these tokens and primitives instead of creating parallel styling systems.

## Principles

SourceBoard should feel modern, minimal, premium and social without looking like a generic SaaS template. The design system favors strong typography, calm neutral surfaces, restrained accent use and deliberate depth.

Liquid Glass is an elevation treatment, not a default page background. Use it for top-level chrome, overlays, floating controls and selected elevated panels. Long-form reading surfaces, dense content and ordinary cards should remain comparatively solid for legibility and predictable rendering cost.

SourceBoard owns all visual styling. `@base-ui/react` supplies headless interaction behavior only; it is not a visual component library. The `motion` package is limited to presence/layout transitions where CSS alone would create duplicated orchestration.

## Theme contract

The only supported theme preferences are:

- `system`
- `light`
- `dark`

`system` is the default. The preference is stored in `localStorage` under `sourceboard-theme`. Invalid or missing values resolve defensively to `system`.

`shared/design/theme.ts` owns parsing, resolution and the theme controller. The root document runs the inline initialization script before hydration so the resolved theme is available before React mounts, reducing theme flash.

The root element exposes:

- `data-theme="light|dark"` — the resolved theme.
- `data-theme-preference="system|light|dark"` — the user's selected preference.
- `color-scheme` — synchronized with the resolved theme.

When the preference is `system`, media-query changes are observed and applied. Explicit Light or Dark overrides ignore system color-scheme changes until the preference returns to `system`.

## Style layers

The visual foundation is split deliberately:

- `app/styles/tokens.css` — shared semantic color-independent measurements, spacing, radii, typography, elevation and related tokens.
- `app/styles/themes.css` — theme-specific semantic surface, text, border, accent and status values.
- `app/styles/glass.css` — reusable glass/elevation recipes plus fallbacks.
- `app/styles/motion.css` — CSS timing/easing recipes and reduced-motion behavior.
- `app/styles/utilities.css` — narrowly scoped shared utilities such as focus treatment.
- `app/styles/base.css` — neutral application baseline and element defaults.

Prefer semantic variables over literal colors inside components. Product phases should extend the token system only when an existing semantic role cannot represent the requirement.

## Liquid Glass rules

### Use glass for

- top navigation or elevated application chrome;
- modal, drawer, dropdown and tooltip surfaces;
- small floating control groups;
- selected contextual panels where background context remains useful;
- presentation layers where the translucency communicates elevation.

### Do not use glass for

- every card on a page;
- long reading surfaces;
- dense data regions;
- nested translucent panels that accumulate blur and contrast loss;
- decorative blur with no hierarchy purpose.

Glass must retain a visible border/highlight and sufficient foreground contrast. Components should continue to look intentional when backdrop filtering is unavailable.

## Component primitives

The public UI entry point is `app/components/ui/index.ts`.

### Core primitives

- `Button`
- `IconButton`
- `Input`
- `Textarea`
- `Card`
- `GlassPanel`
- `Badge`
- `Skeleton`
- `Switch`
- `Checkbox`
- `Avatar`

These components own SourceBoard styling and consume semantic tokens. Variants are generated by the stable helpers in `shared/design/component-variants.ts` rather than ad-hoc class concatenation.

### Interactive primitives

- `Tabs`
- `Modal`
- `Drawer`
- `Dropdown`
- `Tooltip`
- `ToastProvider` / `useSourceBoardToast`

Behavior-heavy primitives use Base UI headless foundations for keyboard, focus and dismissal semantics while keeping all visual presentation in SourceBoard CSS.

Tabs use automatic activation on focus so arrow-key navigation selects the newly focused tab. Overlays support Escape dismissal and appropriate dialog/menu semantics through the headless layer.

### Supporting primitives

- `PresencePanel` — narrow motion wrapper for presence transitions.
- `OverlayActionRow` — reusable presentation helper for overlay actions.
- SourceBoard-owned icon components exported through the same UI barrel.

## Accessibility contract

All new UI should preserve these rules:

- interactive icon-only controls require an accessible name;
- visible input labels should remain programmatically associated with their controls;
- disabled state must be semantic, not merely visual;
- keyboard focus must remain visible;
- overlays must be dismissible by keyboard and return sensible focus through their headless behavior;
- tabs, menus, dialogs, switches and checkboxes must use their corresponding semantic roles/states;
- loading placeholders must not create required interaction;
- status feedback should use appropriate live-region semantics when it represents dynamic feedback.

Do not remove focus outlines without replacing them with the shared focus treatment.

## Motion policy

Normal hover, press, focus and small visual feedback use CSS transitions driven by the shared motion tokens.

The `motion` dependency is reserved for presence/layout transitions. Current typed recipes in `shared/design/motion.ts` use only opacity and transform properties:

- overlay: opacity in/out;
- panel: opacity plus small translate/scale transitions.

The default programmatic transition is `0.22s` with easing `[0.2, 0.8, 0.2, 1]`.

Avoid animating expensive layout properties when transform/opacity communicates the same result. Do not motion-wrap ordinary static primitives.

## Reduced motion

`prefers-reduced-motion: reduce` is a first-class mode, not an afterthought.

- Programmatic transitions resolve to duration `0` through `getMotionTransition(true, ...)`.
- Decorative CSS animation is disabled/collapsed by the reduced-motion stylesheet policy.
- Skeleton shimmer is removed under reduced motion.

Later components must preserve meaningful state changes without requiring animation to understand them.

## Responsive shell

`AppShell`, `TopBar` and `ThemeControl` provide the reusable Phase 0A shell. The Phase 0A visual laboratory is verified at these viewport widths:

- 390px
- 430px
- 768px
- 1024px
- 1280px
- 1440px

Compact layouts must not produce document-level horizontal overflow. New primitives should use `min-width: 0`, wrapping or local scrolling intentionally rather than widening the page.

## Performance budget

Phase 0A establishes these practical constraints for later work:

- keep routine microinteractions in CSS;
- avoid stacking multiple large backdrop blurs;
- animate transform/opacity rather than layout where possible;
- do not introduce a full visual component framework alongside SourceBoard primitives;
- add new client dependencies only when they materially reduce correctness or orchestration complexity;
- keep presentation-only demos free of product persistence, network polling or hidden background work.

Performance should be evaluated in the context of real product screens as later phases introduce data and media. The design system itself should remain a thin shared layer rather than a second application framework.

## Phase 0A visual laboratory

The home route in Phase 0A is intentionally a **visual laboratory**, not a real social feed. It demonstrates the shell, post-like presentation, controls, overlays, theme switching and loading/empty/error/disabled states without pretending authentication, likes, comments or persistence already exist.

Later phases may replace the laboratory with real screens while reusing the same primitives and contracts.

## Dependencies chosen in Phase 0A

- `@base-ui/react@1.8.0` — accessible headless behavior for interaction-heavy primitives; SourceBoard supplies styling.
- `motion@13.2.0` — narrowly scoped presence/layout transitions only.

No full visual component library was added.

## Verification contract

Before merging changes that materially affect this design layer, run the normal repository gate:

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run deploy:dry-run
npm run test:e2e
```

The E2E suite includes theme behavior, keyboard-accessible primitives, reduced-motion behavior and responsive overflow checks.
